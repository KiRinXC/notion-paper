# 阅读笔记写作风格

## 成品定位

成品是“按自己的研究问题重组后的阅读笔记”，不是论文摘要、章节翻译、百科条目或相关工作综述。用户决定关注什么；协作者负责把这些关注点压缩成清晰、可核对、可继续追问的结构。

笔记还应当能在很久以后脱离当前对话独立阅读。读者不应先记得论文的算法编号、写作顺序或协作过程，才能理解当前页在做什么。

优先级从高到低：

1. 保留用户的研究问题、归类方式和判断。
2. 保证事实、公式和证据边界准确。
3. 压缩重复与口语化表达。
4. 补齐现有主题中影响理解的关键步骤与变量。
5. 最后才考虑形式完整。形式完整不得反过来驱动补写。

## 生成顺序

### 1. 建立内容账本

在内部逐块标记，不写入 Notion：

- `论文事实`：PDF 明确陈述的设计、假设或结论。
- `实验事实`：图表和实验直接显示的结果。
- `代码/Artifact 事实`：实现与论文相同或不同之处。
- `用户判断`：我的理解、怀疑、启发、比较和批评。
- `即时疑问`：需要在对话中回答的问题。
- `保留问题`：章末留给后文验证的问题。
- `操作请求`：补公式、建子页、移动媒体等。

同一句包含多个类别时拆开。不能确定来源的内容不得改写为论文事实。

页面已有 `# 润色稿（待确认）` 时，以该标题为输入边界：标题之前是原始笔记，标题之后是上一次生成结果。重跑章节不得从旧草稿提取新的事实、标题或扩写内容；只用新结果替换旧草稿。若用户明确说明自己修改过旧草稿并要求保留，才把这些手工修改作为额外输入进行比较。

用户明确要求根据其手工修改校准后续润色时，先比较差异，再提炼可复用规则。不要把某篇论文的一次事实修正或一次性措辞泛化为长期写作偏好。

### 2. 重建问题骨架

先回答“用户在这一页试图弄清楚哪几个问题”，再生成标题。优先沿用原有标题；允许合并重复标题、把宽泛标题改得更准确，但不得自动套用章节检查表。

标题直接说明这一节承载的内容，使用名词短语或流程名称，例如“候选结构评估”“分析流程”“中间特征保护”。不要使用以下标题：

- 疑问句或带有“如何”“为什么”的提问式标题。
- `Algorithm 1/2` 等依赖论文编号的标题。
- “与某算法的关系”“顺序说明”等解释阅读过程的元标题。
- “我的判断”“我的理解”等无法说明具体内容的通用标题。用户判断应放回它所针对的技术事实、评价指标或限制附近。

典型骨架仅供判断，不是固定模板：

- 摘要：问题 → 现有缺陷 → 核心转向 → 关键结果 → 疑问。
- 引言：防护目标/真实矛盾 → Research Gap → 核心 Insight → 贡献 → 后文验证。
- 背景与威胁模型：系统背景 → 安全目标 → 攻击者能力 → 保护对象与边界。
- 技术页：子问题 → 对象与输入 → 核心机制或替代指标 → 公式含义 → 逐步流程 → 输出与限制 → 后文验证。
- 实验页：claim → 设置 → 结果 → 结果能证明什么 → 耦合、代理量或公平性问题。

只选择当前笔记真实包含的部分。没有内容支撑的标题不生成。

### 3. 压缩成文

- 每个小节首句直接给结论或定义，不用“本文首先”“本节主要介绍”等预告句。
- 后续句子只承担定义、因果、对比、证据或边界中的一种作用。
- 连续步骤、能力集合、输入输出和并列比较使用列表；一个完整判断使用短段落。
- 一个步骤包含多个动作时，在步骤标题下拆成分点；不要把采样、训练、测量和更新塞进一个长段落。
- 使用直接、常见的中文说明技术动作。保留必要英文术语，但首次出现时用人话解释；中文能够准确表达时不要堆叠英文、缩写和抽象名词。
- 公式之后说明“各项是什么、计算什么、输出如何使用”，不复述推导。
- 普通变量、层名、分数和短公式使用 Notion 行内公式；不要用普通行内代码样式表示数学内容。独立公式使用公式块。
- 避免“上面的算法”“后面的流程”“如 Algorithm 2 所示”等依赖阅读顺序的指代，直接写出模块或流程名称。
- 使用 `###` 作为正文主标题，并延续现有页面的橙色标题样式；技术页内部确需分层时再用 `####`。
- `# 润色稿（待确认）` 只作为草稿包装标题，不属于正文结构。

### 4. 写清技术流程

技术页不是把论文术语换成中文，而是让读者能够复述“它拿什么、做了什么、得到什么”。写作前在内部检查：

1. **目标**：该模块具体解决哪个问题，不用宣传式概括。
2. **对象与输入**：处理哪个模型、层、数据、候选集合或硬件状态。
3. **初始化**：哪些权重冻结，哪些参数可训练，哪些候选被建立。
4. **逐步操作**：每一步谁执行、对什么执行、改变什么。
5. **评价与更新**：测量哪个量，它是最终目标还是替代指标，结果如何影响下一步。
6. **输出与用途**：产生结构、排名、密钥、特征或参数后，后续怎样使用。
7. **部署路径**：若涉及系统协同，说明数据在哪些组件之间移动，以及每侧承担什么计算。

这些是完整性检查项，不是固定标题。只为当前页真实涉及的内容生成小节。

流程中的每个步骤优先采用以下结构：

- 步骤标题说明动作，例如“采样候选结构”“训练新增卷积”。
- 分点写出输入、核心操作和状态变化。
- 必要时用一句话说明该步输出为何进入下一步。

不要只写“评估候选结构”“进行敏感性分析”之类的动作标签；必须继续说明评估使用什么数据、计算什么量、如何排序或更新。

论文与官方代码/Artifact 不一致且差异会改变理解时，用简短的“论文与公开代码的差异”提示贴近对应流程。只写差异本身及其影响，不展开核对过程。

### 5. 吸收用户手工修改

- 把用户修改后的稿件视为当前版本基线；保留其标题、归类、术语缩写和格式密度，只修正仍然存在的事实或表达问题。
- 若用户把独立的“证据边界”“补充说明”等段落合并回原有分类，后续默认把事实修正贴着受影响的条目表达，不再另起解释层。
- 即时疑问解决后，只保留理解正文所需的最短结论。删除“原问题为什么产生”“这里回答了什么”等协作过程元叙述，除非问题来源本身构成研究判断。
- 若用户恢复原始标题或分类名称，后续优先沿用；只有原名会造成事实混淆时才提出更名，不静默替换。
- 匹配用户的强调强度。不要自动给每个编号标签加粗，也不要为了显得完整而增加引导句、总结句或边界段。
- 只把结构、密度和语气层面的重复模式沉淀为规则；论文事实、术语选择和单次删改仍按当前页面与 PDF 判断。

## 信息增量边界

润色默认是压缩任务，不是整章扩写任务。以下内容可以增加：

1. 回答即时疑问所必需、且应融入正文的确定事实。
2. 用户明确要求补充的公式及变量含义。
3. 用户明确要求创建的知识子页内容。
4. 修正原笔记事实错误所需的最小解释。
5. 使用户已经记录的技术机制能够独立读懂所必需的局部细节，例如输入、冻结/训练对象、循环中的动作、评价量、输出和后续用途。

第 5 项不是重新翻译论文整节。只沿着用户已经提出的技术主线补齐断点；不要因一次外部搜索顺带加入完整研究史、作者履历、所有攻击变体或与论文无关的定义。

正文完成后检查：除上述允许项外，润色稿的语义范围不应大于原笔记；表达长度通常应更短。如果明显变长，逐段删除没有参与当前因果链或判断的内容。

## 研究笔记语气

- 直接陈述，不写宣传式概括和空泛评价。
- 对论文使用“论文提出/假设/声称”；对结果使用“实验显示”；对实现使用“代码/Artifact 表明”。用户观点贴近其评价对象表达；需要区分来源时使用最短的边界词，不默认另起“我的理解/我的判断”小节。
- 允许明确批评，但必须指出批评落在哪个推理跳步，例如 `proxy ≠ 目标`、`相关性 ≠ 干预收益`、`前缀集合有效 ≠ 排序中每项都关键`。
- 不把用户的探索性语言抹平成权威口吻，也不替用户制造新的“启发”。

## 章节密度

- Abstract 应高度压缩，通常 4–6 个小标题，每个小标题 1 个短段落或一个短列表。
- Introduction 可以展开因果链，但每个小节只服务一个问题。
- Background and Threat Model 追求可扫描性；攻击者能力、不可访问内容和安全边界用列表明确分开。
- System Overview 保持短而完整，只串起系统目标、输入输出、主流程和模块分工；算法细节放入对应技术页，避免在概述中提前展开。
- Technology 页面可以比概述更详细，但必须围绕一个技术子问题。让输入、操作、状态变化、评价方式和输出足以复现逻辑，公式与流程后再说明“它实际优化/证明了什么”。
- Evaluation 按 claim 和证据组织，不按 Figure 顺序逐图复述。
- 知识子页默认以“与当前论文的关系”为边界，通常不逐篇文献展开。

## 强制质量门槛

出现任一情况都先重写，不得写入 Notion：

- 把章节检查表的每个问题都变成标题。
- 按 PDF 段落或论文目录顺序复述，而没有体现用户自己的归类。
- 用“本文主要”“该方法旨在”“首先/其次/最后”填充没有信息量的过渡。
- 把简短线索扩成百科式综述或按作者逐篇罗列文献。
- 重跑时把旧润色稿当成原始笔记，导致错误内容自我延续。
- 新增内容无法回答“它改变了当前章节的哪个判断”。
- 把论文声称、外部资料或用户判断混为同一事实层级。
- 把事实核对过程、即时疑问来源或协作说明写进正文，而结论本身已经能够独立表达。
- 无必要地把用户原有分类改成更抽象的新标题，或为每组事实另起“证据边界”一层。
- 使用疑问句、算法编号、“与某算法的关系”或“我的判断”作为通用正文标题。
- 只列出“采样、训练、评估、更新”等动作名称，却不说明每步处理的对象、状态变化和输出。
- 一个步骤承担多个动作时仍写成大段连续文字，导致流程无法扫描。
- 用普通行内代码样式表示变量和公式，或让数学符号与正文格式混杂。
- 把 proxy、FLOPs、参数量、排序分数等直接写成最终安全或性能结论。
- 删除或回答了保留问题区的问题。
- 大段连续散文掩盖了攻击者能力、步骤、输入输出或对比关系。
- 子页没有回到它与当前论文的关系。

## 写入前自检

1. 用一句话概括当前页真正要解决的问题；无法概括时先重组。
2. 检查每个标题是否能被正文直接回答。
3. 检查每段新增内容是否来自允许的信息增量。
4. 检查事实层级和用户判断是否有边界词。
5. 检查保留问题是否原样保留其开放性。
6. 删除所有操作提示、即时问答痕迹和不服务于当前判断的外部背景。
7. 检查技术流程的每一步是否说明对象、操作和输出；复杂步骤是否已拆成分点。
8. 检查标题是否脱离论文算法编号仍然成立，且没有疑问句或协作元标签。
9. 检查变量与短公式是否使用 Notion 行内公式，而不是普通代码样式。
10. 对照 [examples.md](examples.md) 的合格/不合格示例；未通过则不写入。
